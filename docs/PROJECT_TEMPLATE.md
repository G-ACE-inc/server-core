# PROJECT TEMPLATE

## 目的
新規Projectを、既存資産の再利用を最優先し、不要なファイルと文書を増やさず、短時間・低コンテキスト・低コストで開発できる状態から開始する。

LibralCoreは開発時の設計、Code生成、再利用、局所修正の判断へ適用する。

## 開発開始前の確認
新規Code生成前に次を確認する。

1. 目的と期待結果
2. 同じ責務を持つ既存の設計、Code、Module、型、Schema、テスト、Template
3. そのまま利用できるか
4. 設定・引数・型の調整で利用できるか
5. 薄いAdapterで利用できるか
6. 共通部分を抽出できるか
7. 新規実装が本当に必要か

既存資産を利用しない場合は、複雑化、性能、品質、依存、互換性などの具体的理由を確認する。

## 最小必須構成
- `README.md`
- `.gitignore`
- 技術スタックに対応する実装入口
- 環境変数が必要な場合だけ、値を含まない `.env.example`

`PROJECT_INDEX.md`、`docs/STRUCTURE.md`、`docs/DOC_INDEX.md`、`docs/SPEC.md` を名称だけを理由に一律作成してはならない。

## README.md 最小項目
- Project名
- 目的と期待結果
- 実装入口
- 起動・検証方法
- 主な再利用資産がある場合だけ、その入口
- 現在フェーズ
- 本番運用可否
- 管理者承認が必要な操作

## Single Source of Truth
同じ情報を複数箇所へ記録しない。

正本の優先順位は次とする。
1. Code上の型、Schema、Interface、テスト
2. 実際に利用する単一の設定またはManifest
3. README.md
4. 必要な場合だけ追加する正本文書

CodeまたはManifestから確認できる情報を、手書き文書へ重複記載しない。

## 追加文書を作る条件
READMEまたはCode正本だけでは安全に管理できず、追加文書が開発・再利用・検証・運用コストを実際に下げる場合だけ作る。

追加候補:
- `PROJECT_INDEX.md`: 複数の正本入口を案内する必要がある場合
- `docs/STRUCTURE.md`: 物理構造と責務境界の説明がREADMEでは不足する場合
- `docs/SPEC.md`: 公開仕様または業務仕様を独立管理する必要がある場合
- `docs/DEPLOY_RUNBOOK.md`: 本番デプロイ手順を持つ場合
- `docs/OPERATION_CHECKLIST.md`: 継続運用手順を持つ場合
- `docs/SECURITY.md`: Project固有のセキュリティ境界を持つ場合
- `docs/DOC_INDEX.md`: 正本文書が複数存在し、読込順序が必要な場合

追加理由を説明できない文書は作成しない。

## 5段階層型モジュラーアーキテクチャ
開発AIが設計とCodeを組み立てる論理順序は次で固定する。

```text
Part
  ↓
Feature
  ↓
Component
  ↓
System
  ↓
Application System
```

5段は再利用と局所修正のための論理構造であり、各Application Systemの実行構造や物理ディレクトリ構造を指定しない。

すべての関数、クラス、ファイルを分類しない。再利用範囲、修正範囲、責務混在、依存、テスト対象を判断する範囲だけ分類する。

## Module化判定
Moduleは、同一Project内または別Projectで再利用、交換、独立修正しやすいように、1つの目的と責務へまとめた開発上の再利用単位である。

新規Moduleは次を満たし、再利用または修正コストを実際に下げる場合だけ作る。
- 目的と責務を一文で説明できる
- 入力、出力、依存、前提条件を明確にできる
- Application System固有の値や環境を設定またはAdapterへ分離できる
- 隠れたGlobal Stateや暗黙依存を持たない
- 単独または境界単位でテストできる
- 再利用時に元のApplication System全体を読ませる必要がない
- 追加ファイル、Interface、変換、保守コストが効果を上回らない

## 物理分割
次のいずれかで開発効率または品質が明確に上がる場合だけ分割する。
- 再利用時に対象だけ取り出す必要がある
- 変更理由と依存が明確に異なる
- テスト対象を独立させることで検証コストが下がる
- 権限、秘密情報、実行環境、デプロイ、データ所有を隔離する必要がある
- 同居によって頻繁な競合、誤読、回帰が発生する

次だけでは新規ファイル、ディレクトリ、パッケージ、Moduleを作らない。
- 5段上の分類が異なる
- ファイルが長い
- 将来使うかもしれない
- 一般的な設計例が分けている
- 見た目を整理したい

## AIへ渡す最小情報
- 目的と期待結果
- 対象責務
- 再利用候補
- 入力・出力
- 直接依存と制約
- 関連テスト

最初からProject全体を読ませない。

## テスト最小項目
変更前に次を定義する。
- 入力
- 実行条件
- 期待出力
- 変更される状態
- 変更されてはならない状態
- 既存機能で維持すべき結果
- 異常入力または主要失敗条件の結果

プロセス起動、エラーなし、`True`、空配列、HTTP 200だけでは合格にしない。

## 環境変数
`.env` はcommit禁止とする。

共有が必要なキーは `.env.example` に値なしで記載する。

```env
SERVICE_TOKEN=
REDIS_URL=
```

## GitHub
最小構成をcommitしてから実装を開始する。

作業履歴はcommit / PRを正本とし、現在仕様の文書へ作業履歴を混在させない。

## 禁止
- 5段を物理ディレクトリへ変換すること
- Part、Feature、Componentごとの文書を作ること
- 処理を渡すだけの中継ファイルを作ること
- 再利用候補を確認せず、同じ責務をゼロから生成すること
- 将来利用だけを理由に過剰共通化すること
- READMEと追加文書へ同じ情報を重複記載すること
- 秘密情報をcommitすること
